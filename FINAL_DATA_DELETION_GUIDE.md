# Final participant deletion guide

The command `scripts/delete_final_participant.py` is an administrator-only, **offline** tool for this Final schema. It has been tested against synthetic data in a disposable SQLite database, including dry run, wrong confirmation, rollback after a forced mid-transaction failure, removal from all four app Player tables and native page-time batches, and regeneration of the completed export. It has **not** been tested on PostgreSQL or Heroku. Do not use it on live data until the PostgreSQL rehearsal, backup/restore, offline procedure, and data-governance review are complete.

## Scope and prerequisites

- Match one participant by their Survey Reference ID (the oTree participant code). The tool checks the participant is a Final record and expects exactly one eligibility, one attitudes, six DCE and one household row. It refuses unknown direct participant foreign-key tables or unexpected counts. It removes that participant and the linked rows, chat messages if any, and matching native `otree_pagetimebatch` rows. Household feedback and DCE assignment JSON are in the deleted rows.
- **Schedule an exclusive maintenance window. Stop new participant traffic, flush oTree's in-memory page-completion buffer in every worker, and stop all application workers and background jobs before either preview or deletion.** The database lock does not flush another worker's memory or prevent a stopped worker from being restarted. A normal load-balanced timing export may reach only one worker; if you cannot verify all workers are drained and buffers flushed, do not proceed. Do not delete an actively filling participant concurrently. Perform this only in the separate Final database; do not use it on V5.
- Take and verify a recoverable encrypted backup and record all downstream copies before starting. The command modifies data irreversibly. Confirm operator permissions and secure transport. It does not send email or store the requester's email in the survey database.
- PostgreSQL and SQLite operations are wrapped in a single transaction. PostgreSQL uses exclusive table locks; SQLite uses an immediate write transaction. These do not replace the offline requirement. Unexpected formats or schema stop the operation.

## Operator steps

1. Verify the requester supplies the exact reference ID. Do not request extra identifying information. Identify and protect the matching deletion request in the team's separate, restricted workflow.
2. With Final workers stopped and backup checked, configure `FINAL_DELETION_DATABASE_URL` securely to point to the **Final** database. Do not print or paste credentials into shell history, tickets or screenshots. For an isolated SQLite rehearsal, for example, set it to `sqlite:////absolute/path/to/disposable/db.sqlite3`. The runtime needs the packages in `requirements.txt`.
3. Run `python scripts/delete_final_participant.py REFERENCE_ID`. This is a **dry run** and reports the row counts and number of native timing rows without modifying the database. Verify there is exactly one match and the expected counts. Avoid shared terminal histories when entering IDs.
4. Only when ready, run `python scripts/delete_final_participant.py REFERENCE_ID --execute --maintenance-confirmed` and type the same ID at the prompt. The flag records the operator's assertion that all workers are stopped, timing buffers flushed and backup verified; the program cannot independently verify that assertion. A mismatch or error aborts. Do not repeat against a different database without another preview.
5. Verify the tool reports a committed transaction; run the dry run again and confirm no matching participant is found. Restart the application and regenerate the household completed-only and timing exports; verify the ID is absent and other participant counts and records remain as expected. The SQL test exercises this workflow locally; production-specific verification remains necessary.
6. Delete or regenerate every known research CSV, analysis dataset, downloaded snapshot, screenshot or other managed derivative containing the response. Restrict and document the audit record without keeping the survey answers or unnecessary identifiers. Reply to the requester only through the approved process.

## Limits

The tool cannot erase already downloaded third-party copies, object storage, email, Heroku/router logs, monitoring systems, or database backups. The controller must inventory those copies, arrange deletion or an approved backup-expiry policy, and ensure a restored backup is reprocessed before use. Logs and service metadata may contain participant URLs or references. Do not claim immediate erasure from every system. No automated browser-close deletion or stale-record cleanup is implemented. Failure to meet these conditions blocks live release.
