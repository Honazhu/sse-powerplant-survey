# PostgreSQL check

**NOT TESTED.** No `psql` or `postgres` executable and no isolated PostgreSQL service were established. No existing database was opened for writes, migrated or reset. The local environment has oTree 6.0.15 and SQLAlchemy 1.3.22, but no psycopg2 or psycopg2-binary; production `requirements.txt` contains only oTree. A compatible, reviewed and pinned PostgreSQL driver must be added and tested on Linux before deployment. Do not use SQLite or dyno-local files as production storage.

Static review: `assign_once` uses SQLAlchemy conditional update of a participant claim, then a conditional `allocation_cursor = allocation_cursor + 1` update and reads the resulting cursor; the snapshot and four tasks are populated inside the oTree request transaction, with no explicit commit or SQLite-specific SQL. A unique row-level update should serialize cursor claims under normal PostgreSQL READ COMMITTED semantics, but this is an inference, not a concurrent PostgreSQL result. Verify oTree transaction scope, rollback and ORM identity refresh under the actual stack. Session plan/seed and assignment are database fields. No redesign was made.

Before hosted use, exercise a newly provisioned, explicitly disposable PostgreSQL database: verify initialization without touching existing data; two simultaneous first requests for one participant; at least 50 simultaneous entrants; unique contiguous claim indices and balanced assigned entrants; separate session seeds; transaction rollback at every claim stage; restart and replay; simultaneous conflicting choice submissions; partial dropouts; timing and all exports. Check correct behavior under PostgreSQL's actual isolation level, timeout, connection count and driver authentication. If any fail, stop and review a design-preserving fix. The existing local SQLite regression does not prove PostgreSQL correctness.
