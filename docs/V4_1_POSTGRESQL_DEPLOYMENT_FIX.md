## Driver and Linux build

In a newly created macOS Python 3.11 environment, installing the production requirements succeeded; `psycopg2 2.9.13`, SQLAlchemy 1.3.22 and both `postgres` and `postgresql` dialect aliases loaded, and `pip check` passed. After installing the declared dev requirements, pandas was 2.3.3 and pytest 9.2.0. The package also supplies a CPython 3.11 manylinux2014 x86-64 wheel: the downloaded wheel SHA-256 matched PyPI, `930e7e58b33a4f9c39e7532d7a40147925cf3372baed4229cbebe0cf3ba9ce6b`. Wheel availability is not a Linux or Heroku build test. See [SQLAlchemy 1.3 PostgreSQL](https://docs.sqlalchemy.org/en/13/dialects/postgresql.html) and [PyPI 2.9.13](https://pypi.org/project/psycopg2-binary/2.9.13/).

The binary package bundles native libraries and is selected here to avoid a `libpq`/compiler build requirement. Psycopg's maintainers advise source builds for production and note bundled-library concurrency and security-update tradeoffs; review the [Psycopg installation guidance](https://www.psycopg.org/docs/install.html) before real use. The local test used a Unix socket, not TLS or SCRAM, and does not verify Heroku's connection/authentication. A source-built replacement, if chosen later, requires its own Linux build and regression tests.

## Procfile and dynos

The [official oTree example](https://github.com/oTree-org/oTree/blob/lite/Procfile) contains both web and worker lines. The actual installed 6.0.15 command source is version-specific evidence: `prodserver1of2` launches `otree timeoutsubprocess` as a child and starts one uvicorn worker; `prodserver2of2` describes itself as legacy and simply sleeps. This exact single-web command ran a complete local PostgreSQL survey with `OTREE_PRODUCTION=1` and `OTREE_AUTH_LEVEL=STUDY`. Adding a separate worker would therefore run an idle compatibility process in this version; it was not needed or tested. oTree's [Heroku guidance](https://otree.readthedocs.io/en/latest/server/heroku.html) recommends no more than one web dyno. Reassess the process model if oTree changes.

For a later approved deployment the proposed formation is **one web dyno, zero worker dynos**, plus the already provisioned managed Postgres. Heroku's published pricing on the audit date lists Basic at $7/month per dyno and Essential-0 at $5/month: approximately $12/month combined when a Basic web dyno runs continuously; a second Basic worker would add up to $7/month. Eco's $5 subscription has shared-hour and sleeping restrictions. Usage, actual formation, stack, add-ons, taxes and billing were not inspected. Confirm current [pricing](https://www.heroku.com/pricing/) and [billing](https://devcenter.heroku.com/articles/usage-and-billing) before scaling; this document does not authorize it.

## PostgreSQL transaction review

`assign_once` uses SQLAlchemy conditional UPDATE for the participant claim, then an atomic conditional increment of the round-1 Subsession cursor, reads that cursor, and writes the immutable assignment and four task profiles in the request. No database-specific SQLite statement or schema change was introduced. PostgreSQL UPDATE row locks serialize competing updates to the same row until commit/rollback; under READ COMMITTED the waiting updater observes the committed or rolled-back result. Exact runtime isolation should be confirmed on the actual Heroku database.

oTree 6.0.15's request middleware creates a session and commits responses below 500; 500 responses cause rollback. The middleware normally uses an in-process lock; the installed database code uses SQLAlchemy `StaticPool`, not a normal QueuePool, and context-local sessions. StaticPool normally maintains one connection per engine/process, not a configurable pool of five; reconnection and background processes can affect actual counts. This matters with Essential-0's published 20-connection limit. Monitor the actual connection count and reconnect behavior. Request serialization in one process means the 50-request HTTP test does not prove safety across multiple web dynos; direct competing database transactions were separately exercised, but multi-dyno behavior is not certified.

Stored session plans, participant claims, allocation indexes and task attributes are PostgreSQL fields. A transaction rollback test updated a real synthetic claim and cursor, rolled back, and confirmed neither change persisted. Two connections contended on the same synthetic cursor row; the second waited for the first to roll back, then observed the original value, and was itself rolled back. Refresh, simultaneous duplicate first GET, sequential replay, conflicting simultaneous choice POST and hard process restart were also exercised. This is evidence for the tested environment, not a proof for all failures or isolation settings.

## Tests and limits

Local PostgreSQL was 18.6, obtained as an ephemeral test-only bundled binary, with a new synthetic cluster and database under a private local socket; server default isolation was READ COMMITTED. No Heroku connection or real responses were used. The server and owned survey processes were stopped after testing. Specific checks:

- 50 concurrent eligible entrants, plus duplicate first GETs: 25 block A / 25 block B, allocation indexes 1–50, validated frozen hash and four assigned profiles per entrant.
- Under-18 and consent-refusal exits; complete housing → household → attitudes → completion flow; production-mode STUDY authentication with one additional synthetic complete response.
- Missing attitude form, explicit partial Neutral, invalid value and complete `-2,-1,0,1,2` payload: invalid forms did not save partial data, Neutral remained 0, and Q1–Q5 mapped correctly.
- Each of four completed task durations equalled end minus start and was nonnegative. Refresh preserved start; sequential and simultaneous conflicting replays preserved the first submitted response. A two-task dropout retained completed timings without fabricated completion of later tasks. A hard server-process restart preserved assignments and answers.
- Native export and DCE tasks, wide, long, difference and attitudes exports generated successfully. Merge retained 212 unique task rows for 53 synthetic participant slots, including unassigned/excluded slots; time columns remained valid. No synthetic data or test database is committed.
- Clean Python 3.11 macOS environment: 145 pytest passed, 19 historical CSV fixture tests skipped; separate browser run passed 108 checks and 20 screenshots; Node Cookie Probe passed. One initial browser run failed because the clean checkout lacked the output parent, fixed as described above. One first PostgreSQL harness run had an incorrect test assumption about when the first choice GET allocates; it was corrected and rerun on a second new database, without resetting either database.

The research matrix, survey questions, attitude coding and timing implementation were not modified.
